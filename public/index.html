md2pdf 📄

REST API for rendering a self-contained HTML document into a PDF.

What it is

md2pdf takes a complete HTML document and prints it with headless Chromium. It exists because a PDF needs a layout engine, and the services that want one — the mdbook generator, the wiki's own export — ship deliberately small runtime images with no browser in them. One renderer, its own image, added to a deployment only when the feature is wanted.

The document is sent as html in a JSON body, paper and margins ride on options, and an optional theme supplies a stylesheet, a title block and per-page header/footer furniture.

The renderer fetches nothing. Documents arrive self-contained, so every network request the loaded page makes is aborted — only data: URIs resolve. An <img src="http://…"> written into page content therefore cannot become a request made from inside the deployment's network. Inline your assets before sending.

Example

curl -X POST http://localhost:18509/pdf \
  -H 'Content-Type: application/json' \
  -d '{"html":"<h1>Hello</h1>","filename":"hello.pdf","options":{"theme":"plain"}}' \
  -o hello.pdf

Errors

JSON, as {"error": "…"}: 400 malformed or unknown theme, 401 bad token, 413 body too large, 429 every render slot busy, 500 render failed, 503 no browser.

Themes

GET /themes lists what this instance offers, so a caller can validate its configuration when it builds rather than when a reader clicks a button. 

$ curl -s http://localhost:18509/themes
{"themes":[{"name":"site","label":"Site","options":{}}, … ]}

site is the default and applies nothing — the caller's document is already styled. plain is a readable unstyled baseline. The rest carry a stylesheet, an in-document title block and per-page furniture.

Mounting your own

MD2PDF_THEMES_DIR names extra directories (colon-separated) scanned after the built-ins, so a deployment adds themes without forking the image — and a mounted theme sharing a name with a built-in one wins, which is how you adjust a shipped theme in place. 

docker run -p 18509:18509 \
  -v /srv/brand-themes:/themes:ro \
  -e MD2PDF_THEMES_DIR=/themes \
  ghcr.io/helex-solutions/md2pdf

This is where a theme carrying someone else's visual identity belongs. A wordmark, a palette taken from a brand manual and a postal address are that organisation's, and putting them in a public image would let anyone render a document that looks as though it came from them.

A theme directory

themes/<name>/
  theme.css     the stylesheet
  title.html    in-document title block, once, on page 1   (optional)
  header.html   running header, drawn into every page margin (optional)
  footer.html   running footer                              (optional)
  theme.json    { label, description, options }

title.html and header.html are different things on purpose: the first is ordinary body HTML, the second is drawn by Chromium into the page margin on every page. Chromium has no @page margin boxes and cannot resolve a local()-only @font-face, so a theme ported from a print stylesheet needs both translated — see the repository README.

Health check

GET /health answers 200 only when a browser can actually be launched, and 503 otherwise — so an image whose Chromium is broken is unhealthy rather than quietly failing one request at a time. 

$ curl http://localhost:18509/health
{"status":"ok","engine":"chromium","version":"141.0.7390.54","busy":0,"concurrency":2}
